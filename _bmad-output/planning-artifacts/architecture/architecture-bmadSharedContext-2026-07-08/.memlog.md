- (constraint) GitHub is the fixed platform for authoring, review, and automation — non-negotiable from PRD addendum
- (constraint) Neo4j Community Edition preferred for graph store — architecture preference, not product requirement per addendum
- (constraint) Go for the retrieval API — confirmed from addendum
- (constraint) Local-first pilot: containers from day one; developer-runnable via Docker Compose
- (constraint) Conflict detection is a blocking pre-merge GitHub Actions check
- (constraint) Knowledge authoring: Markdown + YAML front-matter; Dublin Core fields; schema.org/JSON-LD for export; SKOS for taxonomy
- (event) Coaching path selected; spine-only deliverable; workspace initialized
- (decision) Write path (GitHub Actions → graph ingestion) and read path (Go API → graph query) are fully independent; the graph store is the only handoff point. No API write-back to the graph in Phase 1. Binds: no shared runtime coupling between the two paths. Prevents: ingestion logic leaking into the query service.
- (direction) Phase 2 deferred: UI-driven authoring via GitHub Contents API writes to the repo; the merge pipeline then updates the graph. Does not break Phase 1 separation.
- (decision) Paradigm: index-as-artifact. GitHub Action is a build step that produces a versioned index file committed back to the repo. Go API is a read-only query layer over that artifact. No live database required. Binds: all persistence flows through the committed index. Prevents: live-DB connectivity gap between GH Actions runners and local containers.
- (decision) Conflict detection reads the full working tree of markdown files at PR time (files are on the runner filesystem). Does not query the index — the index is a post-merge product. Binds: conflict check is a pure file-processing step. Prevents: needing a live graph queryable from GH Actions runners.
- (direction) Neo4j is no longer required for Phase 1. If richer graph traversal is needed in Phase 2, the versioned index can be imported into Neo4j or another graph store at that point.
- (decision) Index store: plain JSON file committed to the repo. JSON is the stable interchange contract between the write path (Action producer) and all consumers. Binds: the JSON schema is the only coupling point between pipeline and query layer. Prevents: consumer-technology lock-in; any store that can ingest JSON can replace the Go API without touching the pipeline.
- (question) Rule extraction feasibility and ownership: should the pipeline extract canonical rules from documents or should agents extract rules at query time and push feedback for later reuse? Need a sync-safe feedback loop that avoids divergence from source docs.
- (decision) Canonicality rule: documents are the sole editable source of truth. Rules are derived artifacts and are never directly edited by users or agents. Binds: all rule changes must originate from document changes. Prevents: drift between human-authored policy and machine-consumable rules.
- (decision) Regeneration rule: each derived rule carries source provenance (doc path + source span + source hash). When source changes, pipeline reprocesses and replaces affected rules; stale derived rules are invalidated automatically. Binds: sync integrity through deterministic recomputation. Prevents: manual patching of derived rule artifacts.
- (decision) Feedback boundary: agents may emit rule proposals only; promotion into derived rules occurs only in pipeline processing against current source documents. Binds: agent outputs are advisory artifacts, not canonical rule edits. Prevents: out-of-band mutations and desynchronization between docs and rules.
- (decision) Contribution channel invariant: agent-authored domain knowledge is submitted as markdown documents through normal pull requests and must pass the same review and CI gates as human-authored docs before any rule derivation.
- (decision) Schema semantics contract: schema_version governs both structure and normative semantics (conflict severity taxonomy, unknown-value handling, and required field behavior).
- (decision) Determinism contract: ID canonicalization algorithm, provenance span coordinate system, and API result ordering are normative and validated by test vectors in CI.
- (decision) Atomic publication contract: index.json and rule-proposals.json are published from the same build snapshot and bound by a shared build manifest identifier; consumers must reject mixed snapshots.
